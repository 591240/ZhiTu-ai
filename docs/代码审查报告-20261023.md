## P0 · 阻断级

### P0-1 同步 HTTP 阻塞 asyncio 事件循环（最严重）

**位置**
- `server/app/services/image_service.py:42`（`requests.head`，每张图 3s 超时）、`:86`（`requests.get`）
- `server/app/services/route_service.py:104`（公交路径规划）
- `server/app/services/weather_service.py:57`（天气）
- `server/kb/candidates.py:50,95`（POI 候选池）
- `server/kb/embedder.py:73`（query embedding）

**调用链（全部在 async 上下文里）**
```
POST /api/plan/form → plan_service.generate_from_form (async)
  └─ _pool_hint → candidates.city_pool          ← 同步 requests
  └─ 每个 spot → image_service.get_spot_info    ← 同步 requests + N 次 HEAD
  └─ _build_transport → route_service.get_transit_route ← 同步 requests ×2~3/段
  └─ weather_service.apply_to_trip              ← 同步 requests

POST /api/chat/qa → chat_service.qa_stream (async)
  └─ retriever.search → embedder.embed_one      ← 同步 requests
```

**后果**：`requests` 是阻塞调用，会占住 uvicorn 唯一的 worker 线程。冷缓存下一次 2 天行程约 15~20 次串行外部请求（POI + 每段 2 次坐标 + 1 次公交 + 天气），单次 0.2~5s，期间**所有其他用户的请求（包括 `/api/health`）全部排队**。`_pick_image` 里的 `requests.head(timeout=3)` 更是雪上加霜——一个景点最多探测 N 张图。

**修复**
1. 优先：把 5 个模块改造成 `httpx.AsyncClient`，async 到底；
2. 最小改动：在调用处包 `await anyio.to_thread.run_sync(...)`（FastAPI 自带 `run_in_threadpool`），至少把阻塞移出事件循环；
3. `_pick_image` 的 HEAD 探测删掉或改成异步并发 + 更短超时（3s×N 是纯浪费）。

### P0-2 注销账号无效，旧 token 仍可调用全部接口

**位置**：`server/app/deps.py:6-13`

`get_current_user` 只做 JWT 验签，不查库。`/api/user/deactivate` 把 `is_active` 置 false 后，用户手里的 token 在 `jwt_expire_hours=168`（7 天）内依然能调 `/api/trip/*`、`/api/plan/*` 等所有接口。只有 `/api/user/me` 自己做了 `is_active` 检查，形成"半个注销"。

**修复**：在 `get_current_user` 里注入 session 查一次 `User.is_active`（顺带能把 `openid` 从库里取出来，`check_text_security` 依赖它）；或给 token 加 `token_version`，注销时自增。

### P0-3 短信验证码可无限次爆破

**位置**：`server/app/services/sms_service.py:109-123`、`server/app/routers/auth.py:30-39`

`verify()` 只比对码值，不记失败次数；`/api/auth/phone-login` 也没有手机号格式校验。6 位数字码在 5 分钟有效期内可以被脚本跑完（100 万次），一旦命中即以该手机号身份登录。

**修复**：`verify` 前先 `INCR sms:fail:{phone}`，超过 5 次直接 `DEL sms:code:{phone}` 并拒绝；`phone_login` 入口加 `PHONE_RE` 校验。

### P0-4 未配短信 key 时，验证码直接返回给前端

**位置**：`server/app/utils/sms.py`（各 provider 分支 `return True, code`）、`server/app/routers/sms.py:20`、`miniprogram/pages/phone-login/phone-login.js:48`

生产环境一旦漏配 `CHUANGXIN_APP_CODE` / `SMS_API_KEY`，`/api/sms/send` 会把验证码原样返回，前端还会贴心地显示"开发模式验证码：xxxxxx"。等于任何人可以登录任意手机号。

**修复**：`dev_code` 只在 `settings.app_env != "production"` 时返回，生产环境配置缺失应直接抛错（fail fast），而不是静默降级成"谁都能登录"。

### P0-5 `PlanService.last_verify` 是类属性，跨请求串数据

**位置**：`server/app/services/plan_service.py:345`、`:449`、`:574`

```python
class PlanService:
    last_verify: dict = {}      # 类级可变对象
    ...
    self.last_verify = candidates.verify_itinerary(...)   # 每个请求覆盖同一个类属性
```

`plan_service` 是模块级单例，`last_verify` 被所有并发请求共享。A 用户生成行程时，B 用户读到的"校验结果"可能是 A 的；同时这个 dict 会随进程常驻，内容永不释放。

**修复**：改成方法返回值（`_normalize` 直接 `return data, verify`），或写到 `self` 的局部变量而非类属性。

### P0-6 保存行程后前端不回写 id，重复点击产生重复行程

**位置**：`miniprogram/pages/detail/detail.js:397-412`、`:300-315`

后端 `/api/trip/save` 返回 `{id}`，前端 `await request(...)` 后**丢弃了返回值**，`this.data.trip.id` 仍是 `undefined`。后果：
1. 用户点两次"保存"→ 库里两条完全相同的行程；
2. `onShow` 里的 `if (typeof trip.id === 'number')` 永远为假，保存后不会重新拉取，页面数据与库不同步。

**修复**：`const r = await request(...)` 后 `this.setData({ 'trip.id': r.data.id })`（`chat.js:120` 的 `saveAdjust` 已经这么做了，`detail.js` 漏了）。

## P1 · 功能错误（用户直接可见）

### P1-1 行程列表时间全部显示 1970 年

**位置**：`server/app/services/trip_service.py:19`（返回秒） ↔ `miniprogram/utils/format.js:11`（按毫秒算）

```python
"created_at": int(r.created_at.timestamp()),   # 1761000000（秒）
```
```js
const diff = Date.now() - ts    // 1.76e12 - 1.76e9 ≈ 1.76e12
```
实测：`fromNow(nowSec)` → `1月22日`，`new Date(nowSec)` → `1970-01-21`。所以"我的行程"里每一条都显示成 1 月 22 日（或其它 1970 年的日期），永远不出现"今天/昨天/3天前"。

**修复**：后端统一返回毫秒（`int(ts*1000)`），或前端 `fromNow` 里 `if (ts < 1e12) ts *= 1000`。

### P1-2「全部行程」tab 永远是空列表

**位置**：`miniprogram/pages/trips/trips.wxml:11` → `trips.js:29` → `server/app/services/trip_service.py:26-27`

```python
if status:
    q = q.where(Trip.status == status)   # status="all" → WHERE status='all'
```
前端传 `status=all` 表示"不过滤"，后端却当成字面值去查，结果必然为空。

**修复**：后端 `if status and status != "all":`。

### P1-3 收藏页在真实后端下彻底失效（mock 掩盖了它）

**位置**：`server/app/routers/collection.py:23-24` ↔ `miniprogram/pages/collection/collection.wxml:15-20`

后端只返回 `{"id": 收藏记录id, "template_id": 模板id}`，而 wxml 渲染的是 `item.cover / item.title / item.city / item.days / item.route_type`——全部不存在；点击时 `data-id="{{item.id}}"` 传的是**收藏记录 id**，`/api/template/detail` 拿到的是错误的 id。

mock 模式下 `/collection/list` 返回的是完整模板对象，所以在 `USE_MOCK=true` 时页面完全正常，一关 mock 就白屏。这是本项目最典型的"mock 契约与真实后端不一致"事故。

**修复**：后端 join `Template` 返回完整字段，并把 `id` 语义统一为 `template_id`（或前端改 `data-id="{{item.template_id}}"`）。

### P1-4 用过一次"对话微调"后，所有预览行程都被旧数据覆盖

**位置**：`miniprogram/pages/detail/detail.js:60-73`、`chat/chat.js:102`

`app.globalData.adjustTrip` 一旦赋值**永不清除**。`detail.onShow` 的逻辑是：

```js
if (typeof trip.id === 'number') { ...重新拉取... }
else if (app.globalData.adjustTrip) { ...用 adjustTrip 覆盖... }
```

预览态行程（id 是 `undefined` 或 `'fromTpl...'` 字符串）必然走第二个分支。于是：微调过一次 → 回首页 → 用模板生成新行程 → 详情页显示的还是上次微调的那份。

**修复**：`onLoad` 里消费完即清空（`app.globalData.adjustTrip = null`），或给 preview 加一个 `source` 标记区分来源。

### P1-5 对话微调后留下一个空气泡

**位置**：`miniprogram/pages/chat/chat.js:52,103`

`send()` 先 push 了 `{role:'ai', text:''}` 占位，`_adjustSend(q, messages)` 又在同一个数组上 `concat` 一条真正的回复 → 页面上先是一个空气泡，再是回复。

**修复**：`_adjustSend` 里改成 `msgs[aiIndex] = {role:'ai', text: reply}`。

### P1-6 流式请求没有 fail 回调，断网后输入框永久卡死

**位置**：`miniprogram/utils/request.js:98-129`

`wx.request` 只传了 `success`，没有 `fail`。网络异常时 `onDone` 永不触发，`chat.js` 的 `sending` 永远是 `true`，用户再也发不出消息（必须退出重进页面）。

**修复**：补 `fail(err) { finish(err) }`，并加 `timeout`。

### P1-7 `is_vip` / `isVip` 字段不一致，VIP 状态永远丢失

**位置**：`server/app/services/auth_service.py:49`（返回 `is_vip`） ↔ `miniprogram/utils/auth.js:22,62`（读 `payload.user.isVip`）

登录后 `app.globalData.isVip = undefined`。`profile.js` 用 `storage.getIsVip()` 读取的是 `setIsVip(payload.user.is_vip)` 写入的值，所以"我的"页面正常，但任何依赖 `globalData.isVip` 的逻辑都会失效。

**修复**：统一命名（建议后端加 `isVip` 别名，或前端全改 `is_vip`）。

### P1-8 行李清单接口完全忽略入参

**位置**：`server/app/services/chat_service.py:110-116`、`routers/chat.py:39-41`

接口收了 `city / days / season`，返回的是写死的 4 组通用清单（牙刷、充电宝、创可贴）。"带娃去三亚 5 天"和"一个人去哈尔滨 2 天"拿到的结果一模一样。既然接了 LLM，这里应该走 prompt；不接也应该按 season/city 至少做一层模板分支。

### P1-9 手动规划页把自由文本写进了 `time_slot` 字段

**位置**：`miniprogram/pages/manual/manual.js:124`

```js
spots: spots.map(s => ({ name: s.name, time_slot: s.time || '', ... }))
```

`time_slot` 的契约是 `morning/afternoon/evening`，这里写进去的是用户输入的 `"09:00"` 之类。后果：详情页时段标签显示原始时间、`_matchMeal` 的 `typeMap[slot]` 匹配失败、时间轴排序异常。应写 `start_time`，`time_slot` 按时间推断。

### P1-10 每日限流是死代码，限流从未生效

**位置**：`server/app/services/quota_service.py`（全文件）、`server/app/config.py:49`、`miniprogram/config/env.js:37`

全项目 grep 不到任何 `quota_service.check_and_consume` 的调用点；前端 `DAILY_PLAN_LIMIT: 3` 也只在定义处出现一次。也就是说"免费用户每天 3 次"这个宣称的功能完全不存在。

**修复**：在 `plan.py` 的 form/quick 里接入（VIP 放行），或删掉这个模块和配置，避免误导。

## P3 · 架构与规范

1. **mock 与真实后端契约不一致**（P1-3 的根因）：`utils/mock.js` 3053 行，在收藏、时间戳单位、`is_vip` 命名、`trip/save` 返回值上都和 FastAPI 对不上。建议加一组"契约快照测试"：同一份请求，mock 与真实响应结构必须一致。
2. **生产代码依赖 mock 模块**：`index.js:32`、`form.js:42` 用 `mock.mockCities` 渲染城市列表。城市列表是产品数据，不该住在 mock 里；关掉 mock 后这份 3000 行文件仍会被打包进小程序主包。
3. **`env.js` 硬编码局域网 IP**：`BASE_URL: 'http://192.168.101.236:8010'`，且 `USE_MOCK: true` 与上方注释「2026-08-13：已切 false 联调真后端」自相矛盾。换网段即全线超时。
4. **`/api/service/list` 是死接口**：`routers/service.py` 返回 8 个空 `app_id`，前端从未调用（实际用 `env.SERVICE_LINKS`）。
5. **品牌色不统一**：`app.json` tabBar `selectedColor: #0A84FF`，而文档与设计规范主色是 `#4A90D9`。
6. **server 根目录残留**：`tests_offline.py`（与 `tests/` 重复）、`mock_12306_mcp.py`、`migrate_*.py`、`uvicorn.log` 混在业务代码旁。
7. **没有迁移工具**：靠 `create_all` 建表，字段变更不会自动迁移——`migrate_distribution_tracking.py`、`migrate_user_active_feedback.py` 两个手写脚本就是证据。建议引入 Alembic。
8. **单 worker 假设写死在多处**：`chat_service.stats`（进程内计数器）、`_TOKEN_CACHE`、`_spot_cache`、`quota_service._mem`、`sms_service._MEM` 全是进程内状态。compose 里 `UVICORN_WORKERS=1` 暂时掩盖了这个问题，一旦扩容到 2 个 worker，限流、统计、验证码全部错乱。要么统一走 Redis，要么在文档里明确"禁止多 worker"。

### 7.2 schema 迁移与体检（**决定不引 Alembic**）

**为什么不引 Alembic**（这条是判断，不是遗漏）：

- 项目 8 张表、单机部署、个人主体，迁移需求极低；
- 引入它要新增依赖 + `alembic.ini` + 适配异步引擎的 `env.py` + 一份覆盖 8 张表的基线迁移，
  且对已有库必须用 `stamp` 而非 `upgrade`，误操作风险高于收益；
- 审查当时（2026-10-23）的 README 还写着「393 条量级下挂 Milvus 属于过度设计」，
  为了 8 张表引入 Alembic 与那套判断矛盾。
  ⚠️ 这条前提后来被修正了：向量库最终上了 Milvus（实测代价见 README）。但 Alembic 的结论不受影响——
  它反对的是「为一个 8 张表的项目引入迁移框架」，与向量存储选型无关。

**替代方案**（沿用项目已有的幂等脚本模式）：

| 文件 | 作用 |
| :--- | :--- |
| `scripts/migrations/001_collection_unique.py` | 幂等补 `collections (user_id, template_id)` 唯一索引：先删历史重复（保留最早一条），再按「列集合」判断索引是否已存在 |
| `scripts/check_schema.py` | 对比 `models` 与实际库结构，报缺表 / 缺列 / 缺唯一索引 / 多余列。只读，退出码 0=一致 |

实测：构造「无唯一索引 + 含 1 组重复」的旧库 → 迁移清理重复并加索引 → 二次运行幂等跳过 →
插入重复被唯一索引拦截；`check_schema.py` 在新库报「完全一致」，在旧库准确指出
`collections 缺唯一约束 (template_id, user_id)`。

> 顺带修了 `db_init.py`：原来 `SHOW TABLES` 是 MySQL 专有语法，SQLite 下直接语法错；
> 且依赖 `dotenv`/`pymysql` 都没写进 requirements。现改为用 `app.config.settings` 读凭据、
> `inspect()` 取表名、pymysql 按需导入，SQLite 实测可跑且二次运行幂等。

### 7.3 多 worker 状态收敛

| 状态 | 处理 |
| :--- | :--- |
| 每日限流 / 短信验证码 / 发送频率 | 本来就有 Redis 路径，但**缺 Redis 时静默降级**。现在 `APP_ENV=production` 且未配 `REDIS_URL` 直接拒绝启动 |

| `_spot_cache` / `_route_cache` / `_pool_cache` / `_CACHE_MEM` | **故意留在进程内**：这些是纯缓存，多 worker 各自缓存只是命中率下降，不会算错 |
