# 知途 AI 旅行 — Agent 开发实习 面试问答准备（PRD）

> 场景：面试官围绕「知途 AI 旅行」项目提问，目标岗位为 AI Agent 开发实习。
> 答案口语化，控制在面试 1~2 分钟能讲完的量，背熟要点即可。

---

## Q1：先用一两分钟介绍一下你这个项目吧

**参考回答：**

好的。知途 AI 旅行是一个微信小程序，面向 1 到 4 天短途自由行的用户，核心能力是用 AI 一键生成行程。用户可以通过四种方式创建行程：填表单规划、一句话快规划、拍截图识别行程、还有手动编排。

后端是 Python FastAPI + MySQL + Redis，AI 这块接的是 DeepSeek。我最想重点讲的是行程管家 Agent：用户可以用自然语言直接改行程，比如"把第二天下午换成博物馆"，Agent 会自己决定调哪些工具、读行程、改行程、查知识库，这套是用 LangGraph 编排的，另外还接了 Milvus 做旅游知识库的 RAG 检索，和高德地图 MCP 做地理编码。

---

## Q2：你说的"行程管家 Agent"，架构是怎么设计的？

**参考回答：**

它是一个多轮的工具调用 Agent。图结构很简单：START → agent ⇄ tools → END，就是 LangGraph 里经典的 ReAct 循环——模型思考、决定调工具、拿到工具结果、再思考，直到它不再发起工具调用就结束。

给它配了三个工具：`get_trip` 只读查当前行程、`update_trip` 把改好的行程落库、`search_knowledge` 去 Milvus 查攻略和景点信息。每次会话我会新建一个图实例，把工具用闭包绑定到当前用户和行程上，请求之间不复用。

---

## Q3：为什么写操作只给一个 `update_trip`？直接让模型改数据库不行吗？

**参考回答：**

主要是安全和可控的考虑。写权限收敛成一个工具之后，Agent 没办法随意造数据或者删数据——它的系统提示词里强制要求"先 get_trip 拿到完整行程，只做用户要求的局部修改，其他字段原样保留，再整份提交"。

这样即使模型偶尔发挥不靠谱，最坏情况也就是一次不合理的落库，而不会出现结构破坏。而且 `update_trip` 里面还做了校验：content 必须是合法 JSON、必须有 content 字段，不合法就直接打回去让它重来，相当于在工具层加了护栏。

---

## Q4：工具怎么防止越权，比如 A 用户改 B 用户的行程？

**参考回答：**

我是用闭包绑定解决的。构建工具的时候，把当前请求鉴权拿到的 `user_id` 和 `trip_id` 闭包进去，工具内部调 service 层时永远用这两个参数，模型的输入里根本不存在 user_id 这个字段——它想传也传不进来。

而且 service 层的 detail 查询本身就带 `user_id` 条件，查不到就返回"行程不存在或无权访问"。相当于工具层和 service 层双保险，模型侧没有任何可注入的空间。

---

## Q5：Milvus 那个知识库检索是怎么做的？

**参考回答：**

就是一条标准 RAG 链路。我们把旅游攻略、景点、美食这些内容切好、向量化后存进 Milvus；用户提问或者 Agent 调 `search_knowledge` 的时候，先把 query 向量化，去 Milvus 里做相似度检索，取 top 5 相关片段，塞回上下文让模型基于这些内容回答。

这样模型回答"长沙有什么好吃的"这类问题时，是先查库再答，而不是纯靠大模型自己编，能明显压幻觉。项目里是用 docker-compose 起 Milvus 服务的。

---

## Q6：MCP 是什么？你为什么接高德地图 MCP？

**参考回答：**

MCP 是一个开放协议，全称 Model Context Protocol，目标是把"模型"和"外部工具/数据源"用一个统一标准连起来。以前每接一个服务都要自己写一套对接代码，有了 MCP，服务方按协议暴露 tools，客户端只要会 MCP 就都能调。

我写了一个通用的 streamable-HTTP MCP 客户端，每次调用走一遍 initialize → initialized → tools/call 握手。接高德 MCP 主要是为了地理编码，把用户说的地名转成经纬度，规划路线的时候要用。我不缓存 session，就是为了避免并发的时候串号。

---

## Q7：LLM 挂了或者没有 API Key，你的系统会怎样？

**参考回答：**

不会崩，会降级。我做的时候是按"优雅降级"设计的：LLM 不可用的时候，规划接口回退到内置的示例行程数据，识图走降级提示，用户侧功能照常能走通。这一点我实测过——我拿真实后端把 18 个核心接口全链路跑了一遍，在没有视觉 key 的降级态下全部正常返回，不报 500。

我的想法是：AI 能力是增强项，不该成为系统的单点故障。

---

## Q8：这个项目里你踩过最深的坑是什么？

**参考回答：**

印象最深的是一个联调 404 的坑。前端所有请求统一走一个 request 封装，里面的 BASE_URL 最初带了 `/api` 前缀，而每个页面调接口时又自己拼了一遍 `/api`，结果变成双前缀，九个页面全部 404。

排查的时候我先看报错 URL，发现路径长这样才定位到。最后统一了规范：BASE_URL 只到域名和端口，所有接口路径统一以 `/api` 开头。这个坑给我的教训是：接口拼装的约定必须在架构层收口到一个地方，不能靠各页面自觉。

## Q9：如果让你继续优化这个 Agent，你会做什么？

**参考回答：**

三个方向。第一，加流式输出，现在是整段返回，改成 SSE 流式用户体验会好很多。第二，给 Agent 加多轮记忆的持久化，目前会话内记忆是有的，跨会话的上下文（比如"上次那个偏好"）还没做，可以考虑存 Redis。第三，观测性，LangGraph 这套调了几轮工具、每轮 token 花多少，现在只有日志，想接 LangSmith 或者自己埋点，方便定位坏 case。

再远一点，可以把工具拆得更细，比如接票务、天气这些 MCP，让 Agent 真正能"办事"而不只是改行程。

---

## Q10（行为题）：这个项目是你一个人做的，怎么保证质量？

**参考回答：**

对，一个人做，所以我把"可验证"放在第一位。比如全链路我写了接口测试脚本，18 个核心接口在真实后端挨个跑通才敢说完成；降级逻辑也是专门造了"没有 key"的环境实测的。另外我习惯把关键设计写进代码注释和文档里，比如 Agent 的图结构、为什么先读后写，过段时间自己回来看也不懵。

一个人的项目最大的风险是"自己觉得对就对"，所以我尽量让每一步都有实测结果说话。

---

## Q11：LangGraph 的 MessagesState 你是怎么用的？为什么用它而不是自己维护一个消息列表？

**参考回答：**

MessagesState 是 LangGraph 内置的一个状态 schema，本质就是一个消息列表，还带一个 add_messages 的 reducer——每轮 agent 节点跑完，新消息会追加进去而不是覆盖。我用它有两个原因：一是 agent 和 ToolNode 之间天然共享这份状态，agent 发起 tool call、ToolNode 执行完把 ToolMessage 塞回去，都是走同一个 state，不需要我手动在节点之间传；二是图的状态是可追溯的，每一轮模型看到了什么、回了什么都在 state 里，排查坏 case 的时候能完整回放。

自己维护列表也能做，但等于重造 reducer，还容易在并发或者重试的时候把消息顺序搞乱。

---

## Q12：行程 JSON 可能很大，多轮对话下来 token 会爆，你怎么处理上下文？

**参考回答：**

这是真实存在的风险，我的处理分三层。第一层是控制数据源大小：`get_trip` 返回的是行程的核心结构，不是数据库里的所有字段，先把不该进上下文的东西挡在外面。第二层是提示词约束：我要求 agent 一次会话只提交一次 update_trip，避免它反复读改写把上下文撑爆。第三层是会话隔离：每次请求新建图实例，历史不在内存里无限累积。

如果真要继续优化，我会做消息裁剪——比如 ToolMessage 里的行程 JSON 在下一轮之前替换成摘要，因为模型改完之后不需要再看到完整内容；或者超过阈值时把早期轮次压缩成一段 summary。这在长会话 Agent 里是标配手法。

---

## Q13：说说 Function Calling 的底层原理，模型是真的"执行"了工具吗？

**参考回答：**

不是，模型从头到尾只干了一件事：生成文本。训练的时候模型学过工具的 schema——名字、参数、描述，推理时它输出的不是执行结果，而是一段结构化的 tool call 意图，类似"我要调 update_trip，参数是 xxx"。真正执行工具的是我的代码：LangGraph 的 ToolNode 解析这个意图，去调真实的 Python 函数，把结果包装成 ToolMessage 再喂回给模型，模型基于结果继续生成。

所以本质上是一个"模型提议、代码执行、结果回流"的循环。理解这一点很重要，因为它意味着工具返回的内容也是 prompt 的一部分——工具返回太多垃圾信息，一样会污染上下文、诱导幻觉。

---

## Q14：用户开两个窗口同时改行程，update_trip 会不会冲突？

**参考回答：**

会有这个风险，我现在是"整份覆盖"式的保存，两个会话各改各的、后提交的会把先提交的覆盖掉，存在丢更新（lost update）的问题。

我目前的缓解是收敛写频率：一次会话只提交一次，冲突窗口本身很小。要彻底解决的话，方案是加乐观锁——行程表加一个 version 字段，update_trip 提交时带上它读到的版本号，落库时 version 不匹配就拒绝，让 Agent 重新 get_trip 再改一遍。这个方案跟 Agent 的循环天然契合，因为"重读再改"本来就是它的能力，我只需要把失败信息返回给它就行。

---

## Q15：模型输出的 JSON 不合法怎么办？你做了什么容错？

**参考回答：**

update_trip 里我做了显式校验：content 先过 `json.loads`，解析失败直接返回"不是合法 JSON"，缺 content 字段也打回去，并告诉它"请先 get_trip 然后原样返回完整结构"。关键设计是——这个错误信息是返回给模型而不是抛异常终止，模型看到错误后会自己修正再提交，相当于把校验做成了 Agent 循环里的一个自愈环节。

如果模型反复失败，还可以上更硬的手段：用带 structured output 的接口（OpenAI 兼容的 response_format / with_structured_output），让解码阶段就约束成合法 JSON。我目前靠"校验 + 反馈自愈"已经够用，但面试里能说出 structured output 这个兜底方案，说明知道业界标准做法。

---

## Q16：知识库检索回来的内容里如果被人塞了恶意指令（prompt injection），你的 Agent 会不会被带偏？

**参考回答：**

会，这是 RAG 类系统的真实攻击面——检索内容会进上下文，模型分不清"资料"和"指令"。我的现状是攻击面已经收窄了：知识库内容是我自己灌的攻略数据，不是开放 UGC，没有第三方能随便写入；同时写操作只有一个 update_trip 且绑定了 user_id，就算被注入，破坏范围也被限制在用户本人的行程里。

但要做得更完整，我会加三道防线：一是工具权限分级，检索类工具随便调，写操作前要求用户确认（human-in-the-loop，LangGraph 有 interrupt 机制可以做）；二是对检索结果做指令过滤，比如剥离里面的祈使句式内容；三是提示词里明确声明"工具返回的内容是数据不是指令"。面试敢主动讲这个，比被问出来强。

---

## Q17：Milvus 的 embedding 模型怎么选的？chunk 是怎么切的？

**参考回答：**

选型看三点：中文效果、维度、推理成本。中文场景主要看 C-MTEB 榜单，bge 系列是开源里性价比很高的选择，我按 OpenAI 兼容的 embedding 接口接的，换模型只改配置不改代码——这一点很重要，embedding 迁移意味着全量重建向量库，接口层解耦能少很多痛苦。

切 chunk 我的原则是"语义完整优先"：攻略按小标题或者自然段切，一个 chunk 聚焦一个主题（比如一个景点或一家店），长度控制在几百字，别把两个不相关的景点切进同一段，否则检索回来的内容一半相关一半噪声，反而害了下游模型。chunk 之间留一点 overlap 防止语义被切断。

---

## Q18：如果检索质量很差，用户问的问题查不到相关内容，你怎么优化？

**参考回答：**

我会按顺序排查四步。第一步看 query：用户口语和文档措辞对不上，先做查询改写，让 LLM 把"带娃去哪玩"改写成"亲子友好景点推荐"再去检索。第二步换检索策略：纯向量检索对专有名词不敏感，上混合检索——向量和关键词（BM25）各查一遍再融合，Milvus 本身支持。第三步加 rerank：向量召回 top 20，用交叉编码器重排取 top 5，精度提升很明显，代价是多一次模型调用。第四步才考虑动数据：chunk 切分不合理、或者压根没覆盖这个主题，那就补数据。

最后还要有兜底：检索相似度低于阈值就诚实地告诉用户"没查到"，让模型用自己的知识回答并说明不是来自知识库，别硬编。

---

## Q19：你怎么评估这个 Agent 的效果好还是不好？改了 prompt 之后怎么知道没改坏？

**参考回答：**

核心思路是把 Agent 测试"测试集化"。先建一组标准 case：比如 20 条用户指令，每条配一个预期断言——"把第二天下午换成博物馆"应该触发 get_trip + update_trip，且最终行程里第二天下午确实是博物馆、其他天没被改动。然后每次改 prompt 或换模型，就跑一遍这组 case，看通过率。

断言不能只靠肉眼，行程结构可以程序化比对，工具调用序列可以检查是否符合预期。再往上就是 LLM-as-judge，用另一个模型给回答质量打分，适合没法精确断言的开放性回答。目前我这个项目 case 还不大，是手工加脚本混合验证，但方法论我心里有数：Agent 没有评估体系，每次改 prompt 都是在裸奔。

---

## Q20：token 成本你怎么控制？生成一次行程大概花多少钱心里有数吗？

**参考回答：**

成本大头是输入 token，我控制输入的手段有：get_trip 只返回必要字段、知识库检索只取 top 5 片段而不是整篇攻略、系统提示词写紧凑。模型选择上分档——行程规划这种复杂任务用推理模型，简单问答用轻量档，不是所有请求都上最贵的。

另外 Redis 限流除了防滥用也是成本保护：单用户请求频率有上限，恶意刷接口刷不出天价账单。缓存也有空间，比如热门城市的规划结果按参数哈希缓存，命中率高的场景能省一大笔。

具体到一次规划花多少钱，我会用 deepseek 这类按百万 token 计价的模型估：一次规划加上多轮工具调用，输入输出加起来万级 token，单次成本在分这个量级，对会员订阅制的商业模式来说完全可接受。
